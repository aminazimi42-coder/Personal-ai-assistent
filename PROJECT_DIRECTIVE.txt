TARGET ARCHITECTURE
Keep Flask as a modular monolith unless evidence requires otherwise.
Target layers:
Browser/UI → API → Auth/AuthZ → Application/Domain Services → AI Orchestration/Tools → Persistence/PostgreSQL.
Cross-cutting: configuration, validation, errors, logging, metrics/tracing hooks, rate limiting, security, testing, migrations, safe caching.
Keep routes thin. Centralize auth, validation, config, DB access, AI client/orchestration, and errors. Avoid duplicate logic.

1. REPOSITORY HYGIENE
Create a professional .gitignore covering .env/secrets, venv, caches, __pycache__, local DBs, logs, editor/OS artifacts, temporary files and generated sensitive files.
Audit tracked files for secrets/private artifacts.
Safely remove local/generated venv from Git tracking only after confirming it is not required by the application; do not blindly delete the user's environment.
Review personal/private images and orphaned artifacts; preserve required assets and replace references before removal.
Use semantic commit messages.

2. CONFIGURATION
Create safe .env.example with variable names only.
Centralize validated environment configuration, including DATABASE_URL, OPENAI_API_KEY, OPENAI_CHAT_MODEL, environment, allowed CORS origins, token lifetime, rate limits, AI budgets and logging level.
No secrets in repository.
Remove or properly integrate unused configuration only when justified.

3. DATABASE/PERSISTENCE
Replace request-time DDL with a professional migration system.
Implement deterministic migrations, transactions, connection pooling, correct connection lifecycle, foreign keys, indexes, UTC/timezone-safe timestamps, domain constraints, consistent schemas and safe upgrade paths.
Do not destroy existing user data.
Do not keep duplicate CREATE TABLE/schema definitions.
Do not depend on a public /init-db endpoint for production initialization.

4. AUTHENTICATION/AUTHORIZATION
Centralize authentication.
Implement secure signup validation, normalized emails, strong password policy, bcrypt, secure token lifecycle, expiration, revocation, consistent 401/403 responses, anti-enumeration login behavior, logout, ownership checks and authenticated private AI operations.
Design token storage so a database compromise does not unnecessarily expose reusable bearer credentials.
No anonymous costly OpenAI operations by default.

5. API
Use HTTP semantics correctly.
GET only retrieves; POST creates/actions; PATCH/PUT updates; DELETE removes.
Remove side-effecting GET appointment creation.
Move primary AI interaction from query strings to POST JSON.
Define consistent success/error structures.
Add centralized 400/401/403/404/409/429/500 handling.
Never return raw exception strings.
Validate types, lengths, enums, timestamps, IDs, request sizes and AI-generated values.

6. AI/OPENAI
Build one centralized AI orchestration layer separating:
conversation understanding; response generation; intent/action classification; tool selection; tool execution; validation; confirmation; persistence; final response.
Do not allow raw LLM output to mutate DB directly.
Validate all structured AI output against explicit schemas.
Centralize OpenAI client configuration.
Use explicit timeouts, bounded output tokens, bounded context, safe retries for transient errors, graceful failures and configurable models.
Never expose SDK exceptions or API keys.

Minimize token usage and cost without degrading required quality.

- concise system prompts
- context minimization
- bounded conversation history
- summarization for long histories
- structured outputs
- strict output limits
- model routing by task complexity

- elimination of duplicate LLM calls
- safe caching/deduplication
- relevant-context filtering

- message length limits
- per-user/request AI budgets
- usage accounting
- abuse protection
